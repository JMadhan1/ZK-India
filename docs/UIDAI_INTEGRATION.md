# UIDAI Integration — the demo-vs-real gap

This is the single most important document for anyone assessing how close this
prototype is to a deployable system. Read it before believing — or doubting — any
claim about what ZKGate proves.

## What is real

The **zero-knowledge layer is fully real**. Proofs are genuine Groth16 proofs over
BN128, generated by snarkjs and verified by an independent Python implementation
(`backend/services/groth16.py`) that is cross-checked against snarkjs and rejects
tampered proofs, off-curve points, and out-of-field signals. A citizen who is 17
genuinely cannot produce an `age ≥ 18` proof. Replays are genuinely caught.
Nothing about the citizen is genuinely transmitted.

## What is stubbed

Every circuit takes a private input `signature_valid` and asserts it equals 1. In
a real deployment, `signature_valid = 1` must mean *"the Aadhaar offline eKYC XML
carried a valid RSA-SHA256 XMLDSig signature from UIDAI."* In the prototype, the
citizen's own client sets that bit (`sdk/src/aadhaar.js → verifySignature`), and
for the synthetic test XMLs it always sets it to 1 in **demo mode**.

Concretely, the gap is this: **a malicious citizen could fabricate an XML with any
date of birth, set `signature_valid = 1` themselves, and produce a
"valid" proof of a false fact.** The ZK maths would check out; the attestation that
the underlying data came from UIDAI would be the lie.

The system is honest about this. Every proof built in demo mode is tagged
`demo: true`, the backend reports `trust_level: "demo"`, and a production verifier
is expected to refuse demo proofs.

## Why it's stubbed (and not hidden)

Two reasons, one practical and one that is itself a design decision.

Practical: verifying UIDAI's signature requires UIDAI's published certificate and,
to do it *properly*, the XMLDSig canonicalisation and RSA verification must run
**inside the circuit** — otherwise the client is still just asserting a bit, only
after checking it locally, which a malicious client skips. In-circuit RSA-SHA256
over canonicalised XML is a large circuit (tens of thousands of constraints) and a
project of its own.

Design: doing it half-way — verifying the signature in the client but not in the
circuit — would *look* secure while providing no more real assurance than the
current stub. We chose the honest stub with a loud `demo` flag over a
security-theatre partial implementation.

## How to close it

Three approaches, in increasing order of soundness:

1. **Server-side XML submission (weakest, breaks privacy).** Citizen sends the XML;
   server verifies the signature and issues a signed attestation the citizen then
   proves over. Simple, but the server now sees the XML — defeating the point.

2. **Client verification + issuer-signed commitment (moderate).** A trusted
   enrolment step verifies the UIDAI signature once and issues the citizen a signed
   credential (e.g. a BBS+ or EdDSA signature over a commitment to their
   attributes). The circuit then proves knowledge of that issuer signature — a far
   smaller circuit than in-circuit RSA. This is how most production ZK-identity
   systems (e.g. Anon Aadhaar's lineage, EU digital identity wallets) actually work.

3. **Fully in-circuit UIDAI signature (strongest, heaviest).** The circuit itself
   verifies the RSA-SHA256 XMLDSig against UIDAI's public key over the canonicalised
   `SignedInfo`. No trusted enrolment step; the proof itself attests provenance.
   Largest circuit, longest proving time.

For India specifically, **option 2** is the pragmatic target: it keeps proving fast
enough for a phone, needs no server to see the XML, and reduces the trusted step to
a one-time credential issuance that can itself be audited.

## The wiring that's already in place

- `sdk/src/aadhaar.js → verifySignature(xml, uidaiPublicKey)` — returns
  `{valid, demo}`; passing a real key currently throws rather than pretending, so
  the unfinished path is impossible to use by accident.
- `test-data/uidai_public_key.pem` — instructions to fetch the real UIDAI cert.
- The `signature_valid` signal exists in every circuit and is already constrained
  to 1 — so an in-circuit signature check slots in by replacing the assertion with
  the verification component; the rest of each circuit is unchanged.
- The `demo` flag threads from the SDK through the API to `trust_level`, so the day
  real attestation lands, verifiers flip from accepting `demo` to requiring
  `attested` with no other change.
